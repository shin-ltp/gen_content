## 3. 定時方案 v3（単一段・日中パイプライン。火〜土 07:00 JST 起動）

v2 の二段構成は否決された。夜間の事前収集では前日の素材しか得られず、深掘り選題は当日引け後に
やり直す必要があるためである。v3 は **07:00 に一度だけ起動**する。この時点で当日の引け相場、
引け後決算、WSCN の隔夜解説、Five Things（06:04）、Trading Day（06:17）がすべて揃い、
07:30 の Reuters 日本語は収集過程で自然に取り込まれる。サブエージェントの並列で 10〜11 時間の
直列作業を薄め、**目標は当日 16:00 前の公開**。

### 役割編成（オーケストレーター主タスク 1 件 ＋ 5 種類のサブエージェント）

| 役割 | 責務 | 担当 item（pipeline.json） |
|------|------|---------------------------|
| オーケストレーター（主タスク本体） | init／ハートビート／監視／代替方針決定／公開 | publish |
| 収集 | Phase 0 全経路収集 ＋ verify | collect |
| 選題 | Phase 1 で B1〜B4 ＋ A/C/D 要点を確定 | triage |
| B ライター＝オーケストレーター自身 | B1→B4 を順に深掘り執筆＋査読（各主題約 1.5 時間）。1 主題を固定したら即納品し、次の主題へ進む | draft-B1..B4 |
| ACD ライター（サブエージェント） | A→C→D の順で執筆＋査読 | draft-A / draft-C / draft-D |
| TTS ワーカー（サブエージェント） | draft-* が done へ変わったら取得。ローカル fishaudio で **直列** 合成（GPU 排他的、並列不可） | tts-* |
| 視覚（サブエージェント） | 全稿固定後に画像検索・生成 → HTML 視覚内容 | visual-assets / visual-html |

### 引き継ぎ規約: pipeline.json（唯一の事実源）

- パスは `daily-output/<date>/pipeline.json`。読み書きは
  `node us-stock-daily/tools/pipeline/pipeline.mjs` のみ（原子書き込み。CLI はファイル先頭コメント参照）。
- ライフサイクル: `pending → running → reviewing → done`（または failed/skipped）。
  **ライターが draft-X を done にした時点で「TTS 取得可能」を意味する**。TTS ワーカーは取得時に
  tts-X を running にし、完了時に done にする。各 item の書き込み責任者は owner の一者のみで、
  他の役割は読み取り専用。
- オーケストレーターは 10 分以内の間隔で `alive` ハートビートを実行する。

### 内容完全性契約（2026-09-09 改訂。違反は pipeline.mjs が自動拒否する）

1. **done 項目の巻き戻し禁止**: `set` で `done → done 以外` は常に拒否され、メール告警が送られる。
2. **skipped からの黙示的な復活禁止**: `skipped → running/pending/done` の直接変更は拒否される。
   復活は必ず `set --date D --id ITEM --state running --repair` を使う（`--repair` は
   `--date` の直後の独立フラグとして渡すこと。行末に置くとパーサに値として吸収される）。
3. **内容項目への skipped 禁止**: `draft-*` / `tts-*` / `spotcheck` / `publish` に
   `--state skipped` を設定しようとすると拒否される。時間不足でも削るのではなく公開を順延させる。
4. **当日のみ変更可能**: `--date` が現在の東京日付と異なる変更は拒否される。過去分の修正は
   init への明示的な `--force` が前提で、通常運用では使わない。
5. **告警は自動送信**: `check` / `deadlines` が exit 2 のとき、pipeline.mjs は問題ごとに
   30 分バケットで重複排除したメールを送る。呼び出し側が手動で `notify-email.mjs` を
   重ねて呼ぶ実装は不要。

### 障害監視と自動復帰

1. **失速監視**: 約 15 分ごとに `check` を実行。判定は、item が running/reviewing に工程しきい値を超えて
   滞留（collect 50 / triage 50 / write-a 45 / write-cd 60 / write-b 80 / tts-short 55 /
   tts-b 105 / visual 90 / render 90 / final 45 分）、failed の発生、またはハートビート 15 分超 → exit 2。
2. **復帰動作**: attempts<2 なら `set --retry` で pending へ戻し、owner が再実行する（TTS は sentence
   キャッシュで増分再合成、描画は分段成果物から継続）。attempts≥2 は failed にし、
   `tools/collect/notify-email.mjs` でメール通知 → 代替方針に従って継続し、全体停止にはしない。
3. **締切時点の扱い**: 起動後、毎時に `deadlines` を実行。7 検査点
   （08:20 / 10:30 / 12:45 / 13:30 / 14:45 / 15:30 / 16:00）で BREACH の場合は
   `notify-email.mjs` で告警し、遅延している工程を優先して継続・補完する。
   **時間不足を理由に内容を切り捨ててはならない。** B1〜B4 ＋ A/C/D の全件を維持し、
   圧縮・統合・静音パッド・音声のみ先行公開を禁止する。公開が遅延する場合は
   spotcheck 完了後に全体を順延して公開する。正味の内容・セグメント・TTS は完成させる。
4. **オーケストレーター自身の停止**: 独立 watchdog automation（08:00〜15:00 の毎時）が `check` を実行。
   ハートビート消失かつ done の進行がない場合にメール警報。主タスク再起動後は pipeline.json の
   達成点から継続する。

### 並列原則（成果物へ相互影響しない範囲）

1. 分段増分 TTS: 固定した一段から合成し、改稿は変更文だけ再合成する（sentence キャッシュ。9/1 検証済み）。
2. TTS は GPU のみを消費する。QA、visual.html のスクリーンショット、投稿素材準備はすべて並列に実行する。
3. 概念図・画像検索は imagegen API（ネットワーク待ち型）を使い、執筆および TTS と並列にする。
4. Remotion 描画（CPU 密集）と TTS（GPU）は時間をずらし、資源を取り合わない。

### ローカル TTS（WSL2）起動契約

- 正式合成時、`fish_local_engine.ensure_server()` が自動で
  `tools/fishaudio-s2-pro/wsl/start_server_guard.ps1` を呼ぶ。ガードは HTTP OPTIONS で
  既存サービスを先に確認し、健全なサーバを殺さない。起動待ちは既定 900 秒
  （torch.compile の冷起動 5〜8 分を含む）。
- `auto` エンジンは WSL2 専用として動作し、起動に失敗した場合は Mac へ黙ってフォールバックしない
  （代わりに明示的な RuntimeError）。Mac は `--engine mac` を明示したときのみ使う。
- dry-run (`--dry-run`) はサーバを起動しない。実合成の直前に起動契約が発火する。
- 定時タスクは WSL 起動を前提とする。ガード呼び出しが沙盒の承認を求めた場合は、
  承認後に同じコマンドを再実行し、失敗を理由に別エンジンへ置き換えない。

### カレンダー規則

- 火〜土（JST）に実行: 前日が米国株式取引日であれば制作する。米国の祝日は通常どおり起動し
  （A 段は休市日用テンプレートを使う）。
- 冬時間切り替え週（11 月第 1 週）: 引けデータは 06:00 以降に揃うが、07:00 起点は変更せず、
  verify-collection の完全性だけ観察する。
