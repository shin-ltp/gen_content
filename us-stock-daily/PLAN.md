## 一、番組定位

毎日30-40分の米国株深層分析番組。日本の個人投資家向け。単なるニュース読み上げではなく：
- **専門情報提供者**: 複数の権威ある情報源を集約し、専門的で深い解説を提供する
- **実践的アクション指導者**: 実行可能な価格水準とポジションサイズの目安を示す
- **長期投資の提唱者にして個人の守り手**: リスナーの分散投資・適正ポジション管理・リスク管理への意識を高め、長期投資の理念で「個人がウォール街に勝つ」ことを目指す

## 二、マルチエージェント・ワークフロー全体設計

### 2.1 設計思想

かつての設計では、制作要件が1ファイルに集中しており、単一エージェントが全工程を担当すると「手抜き（偷工减料）」が発生しやすかった。本設計は以下の原則でこれを解決する：

1. **工程の分割（Phase 化）**: 制作を直列／並列可能なフェーズに切り分け、各フェーズを独立したサブエージェントが担当する。
2. **責任の局所化**: 各エージェントは「自分の Phase の入出力と品質ゲート」だけに集中する。全体構成判断はスケジューラ（PLAN）と後段フェーズが担う。
3. **成果物の永続化**: 各フェーズの成果物は必ずディスクに保存する（メモリ受け渡し禁止）。これにより後段エージェントは常に最新の確定成果物を読める。
4. **段階的品質ゲート（Staged Checks）**: フェーズ完了ごとに検査を通過しない限り次フェーズに進まない。手抜きを構造的に防ぐ。
5. **遅延取得（Lazy Fetch）**: 重い処理（画像・チャートのクロール等）は必要になった瞬間にだけ実行する（Phase 3 参照）。

### 2.2 フェーズモデル概観

| Phase | 名称 | 担当エージェント | 主出力 | 状態 |
|-------|------|------------------|--------|------|
| **0** | 情報収集 | `collector-agent` | `collection/`（素材ファイル群＋索引） | ✅ 定義済み |
| **1** | テーマ選定・構成 | `triage-agent` | `production/outline.md` | 🚧 後日補完 |
| **2** | スクリプト制作 | `scriptwriter-agent`（コーナー別に並列可） | `production/draft-*.md` | 🚧 後日補完 |
| **3** | 視覚素材取得（遅延クロール） | `asset-fetcher-agent` | `assets/` | 🚧 後日補完 |
| **4** | 品質検査 | `qa-agent`（複数レンズで並列可） | `review/qa-report.md` | 🚧 後日補完 |
| **5** | 統合・最終化 | `integrator-agent` | `YYYY-MM-DD.md`（完成スクリプト） | 🚧 後日補完 |

### 2.3 タスクスケジューリングと依存関係（DAG）

```
[Phase 0: 情報収集]
        │  （品質ゲート#0 通過で確定）
        ▼
[Phase 1: テーマ選定・構成]
        │  （品質ゲート#1 通過で確定）
        ▼
[Phase 2: スクリプト制作] ──採用素材をマーク──▶ [Phase 3: 視覚素材取得]（トリガ駆動・並列）
        │                                              │
        │  （品質ゲート#2）                             │ （品質ゲート#3）
        ▼                                              ▼
[Phase 4: 品質検査] ◀────────────────────────────────┘
        │  （品質ゲート#4：不合格なら Phase 2 へ差戻し）
        ▼
[Phase 5: 統合・最終化]  → 完成スクリプト ＋ 俳句OP ＋ 免責
```

- Phase 0→1→2 は厳密に直列（前段の確定成果物が入力）。
- Phase 3 は Phase 2 の進行に伴い**インクリメンタルに起動**（採用された素材から順にクロール）。Phase 2 と並行。
- Phase 4 は Phase 2・3 の両方が一段落してから実行。不合格項目は Phase 2（必要なら 3）へ差戻し。

### 2.4 段階的品質ゲート（Staged Checks）

各 Phase に **Entry Criteria（開始条件）／ Definition of Done（完了定義）／ Gate Check（検査）** を定義する。Gate を通過しない限り次 Phase に進まず、`status.md` に結果を記録する。

| Gate | 対象 Phase | 検査の概要 | 合格で進む先 |
|------|-----------|-----------|--------------|
| #0 | 情報収集 | カバレッジ・定量・関連性・網羅性・重複・索引完全性（詳細は 3.7） | Phase 1 |
| #1 | テーマ選定 | TODO | Phase 2 |
| #2 | スクリプト | TODO | Phase 4（+ Phase 3 並行） |
| #3 | 視覚素材 | TODO | Phase 4 |
| #4 | 品質検査 | TODO（不合格→Phase 2 差戻し） | Phase 5 |

### 2.5 日次ワークスペースとステータス管理

1日＝1ディレクトリ。全 Phase の成果物を同じディレクトリに集約し、進行状況を `status.md` で一元管理する。


## 三、Phase 0：情報収集（詳細仕様）

### 3.1 目的と収集原則

> **収集の鉄則：宁可多取、不可漏掉（多く取り過ぎてもよいが、絶対に漏らさない）**
>
> 収集エージェントの役割は「幅広く集めること」であって「絞り込むこと」ではない。
> - 米国株に関連する情報は**可能な限りすべて**収集する。重複・些末は気にしない（後段の Phase 1 が選別する）。
> - 取捨選択は collector の仕事ではない。**質の判断・優先度付けは triage-agent（Phase 1）に委ねる。**
> - 「これは使うか不明」でも残す。使わなかった素材が残るのは正しい状態。

> **収集前の前提: データの鮮度階層（3.9.2）**
> 「多く取る」のは**変動データ（Tier A）**について。決算財務・マクロ指標・経済カレンダー・目標株価などの**定期更新データ（Tier B）**は毎日再取得せず、**ローカル DB（3.9）から読む**。DB 上で FRESH なら再取得を省き、当日素材の `key_data` に DB 値を転記すればよい。「多く取る」原則は「DB を都度最新化しなくてよい」とは矛盾しない ― Tier B は別途の定期／能動更新機構（3.9.4）で保つ。

### 3.2 遅延取得戦略（テキスト＋URL 先行、画像は後で）

重い取得処理（Web ページのスクロール・画像保存・チャート抽出）は Phase 0 では**一切行わない**。

| 何を | Phase 0（今） | Phase 3（後で） |
|------|--------------|----------------|
| 本文テキスト・要点 | ✅ 保存 | — |
| ソース URL | ✅ 保存 | — |
| 核心データ（数値） | ✅ 抽出して保存 | — |
| 出所・時刻 | ✅ 保存 | — |
| スクリーンショット | ❌ 取得せず、`assets_needed` でフラグだけ | ✅ 採用時にクロール |
| 記事内チャート・画像 | ❌ 取得せず、フラグだけ | ✅ 採用時にクロール |
| 企業ロゴ・概念図 | ❌ | ✅ 必要時に取得（ロゴは `assets/brands/` 共有キャッシュ優先 — 3.10） |

> Phase 2 で素材がスクリプトに採用された瞬間、当該素材の `adopted` を `true` にし、Phase 3 の asset-fetcher-agent が `url` を読んで詳細（画像・チャート）を取得し `assets/` に保存する。
>
> **ロゴは例外（3.10）**: 企業・メディアロゴは回限定ではなく**全日共有キャッシュ** `assets/brands/` から取得する。キャッシュにあれば再取得せず、なければ検索DL → 保存 → 次回キャッシュ命中。

### 3.3 収集対象カテゴリと情報源マップ

収集は以下6カテゴリで行う。各カテゴリの情報源は **第七章「情報源一覧」** を参照。

| カテゴリ | ID 接頭辞 | 収集内容 | 主情報源 |
|----------|-----------|----------|----------|
| 市場データ | `MKT-` | 指数・為替（ドル円含む）・債券利回り・コモディティ・暗号・心理指標 | Finviz, TradingView, Yahoo, CNN Fear&Greed |
| マクロ経済 | `MAC-` | 経済指標・FRB・財政・金利予想 | Investing.com, CME FedWatch, FRED, BLS, BEA, 財務省 |
| 大手リサーチ | `RES-` | 投資銀行レポート・アナリストレーティング変更・目標株価 | Goldman/JPM Research, TipRanks, Seeking Alpha |
| 個別株・セクター | `STK-` | 決算以外の個別株・セクター動向・バリュエーション材料 | SEC EDGAR, 各社IR, SemiAnalysis, 媒体 |
| 決算 | `ERN-` | 決算発表・ガイダンス（決算シーズン中心） | SEC EDGAR, 各社IR, Reuters |
| ニュース速報 | `NWS-` | 当日の速報ニュース（M&A・規制・地政学等） | Bloomberg/WSJ メール, CNBC, Reuters, AP |

### 3.4 素材ファイル標準フォーマット

素材1件＝1ファイル。カテゴリ別フォルダに `{ID}.md` として保存。フロントマターでメタを管理し、後段エージェントが検索・状態更新できるようにする。

```markdown
---
id: STK-20260714-007              # {CAT}-{YYYYMMDD}-{連番}  一意ID
category: stocks                   # market|macro|research|stocks|earnings|news
ticker: NVDA                       # 該当銘柄（なければ空）
title: エヌビディア、需要見通しでGS目標株価引き上げ
source: Goldman Sachs Research     # 情報源名
source_type: research              # official|research|media|social|data
url: https://www.gs.com/...        # ソースURL（必須）
relevance: us-stock                # 米株関連（基本 us-stock）
collected_at: 2026-07-14T06:32     # 収集日時
collector: collector-agent         # 収集エージェント名
priority: TBD                      # A|B|C|TBD（Phase 1 が後で付与。収集時は TBD 可）
key_data:                          # 抽出した核心データ（リスト）
  - "目標株価 190ドル（+22%）"
  - "レーティング 買い継続"
assets_needed: [chart, table_image] # 後期取得したい画像種別（なければ []）
assets_status: none                 # none|pending|fetched（Phase 3 が更新）
adopted: false                     # スクリプト採用フラグ（Phase 2 が true に）
status: raw                        # raw|verified|adopted|dropped
---

## 概要
（本文テキスト・要点を簡潔に）

## 原文抜粋
（必要に応じて引用テキスト。長すぎる場合は要点のみ）

## 備考
（関連リンク・クロスチェック元・収集時の所感など）
```

**フォーマット規約:**
- `id` は カテゴリ接頭辞 + 日付 + 3桁連番。同日内で一意。
- `url` は**必須**。URLなき情報は原則採録しない（出所追跡不能のため）。
- `key_data` は後段のデータ密度チェック（第五章）の原料。具体的な数値を入れる。
- 収集時点では `priority=TBD` `adopted=false` `status=raw` でよい。

### 3.6 収集サブワークフロー（手順）

collector-agent は以下を順に実行する。各ステップで取得した素材を即座にファイル化する（メモリに貯めない）。

```
0. ワークスペース初期化
   - daily-output/YYYY-MM-DD/{collection,assets,production,review}/ を作成
   - status.md を todo で初期化
0.5. DB ヘルスチェック（定期更新データ層 — 詳細は 3.9）
   - `db/refresh.py` を実行し、`effective_until <= now` の定期データ（財務／マクロ／経済カレンダー／目標株価）を一括更新（定期更新: 3.9.4-①）
   - `data_catalog` の次回予定日を確認し、当日のマクロ発表イベントを把握
   - 以降のステップで Tier B データは DB 経由で取得（FRESH なら再取得しない／STALE なら能動更新: 3.9.4-②）
1. 市場データ収集（MKT）
   - 固定放送資産（第二章2.xの固定資産リスト）を網羅：指数/為替/債券/コモディティ/暗号/心理
2. マクロ収集（MAC）
   - 経済カレンダーの当日イベントを**漏れなく**拾う（予想・前回値付き）
3. レーティング・リサーチ収集（RES）
   - 当日の主要レーティング変更・目標株価改定を幅広く
4. 個別株・セクター収集（STK / ERN）
   - 当日の注目銘柄・セクター動向、決算シーズンは ERN を厚く
5. ニュース収集（NWS）
   - 朝のメール・リアルタイム・ソーシャルを幅広く
6. 索引作成
   - 00-manifest.md を生成（カバレッジチェック付き）
7. Gate #0 自己点検 → status.md に PASS/FAIL を記録
```

### 3.7 Phase 0 品質ゲート（Gate #0 検査基準）

Gate #0 は collector-agent の自己点検＋スケジューラの承認で構成。**すべて合格で Phase 1 へ**。

| # | 検査項目 | 基準 | 不合格時の対応 |
|---|----------|------|----------------|
| 1 | **カバレッジ** | 6カテゴリすべてに素材 ≥1件。情報源チェックリストの「必須源」を網羅 | 不足カテゴリを追加収集 |
| 2 | **定量** | 1日あたり素材 ≥ 30件（決算/FOMC週は ≥ 50件）を目安 | 追加収集 |
| 3 | **関連性** | 全素材 `relevance=us-stock`。米株無関係は除外 | 除去 |
| 4 | **網羅性（最重要）** | 「固定放送資産」と「当日の経済カレンダーイベント」に**漏れがないこと** | 漏れを補収集 |
| 5 | **URL 完備** | 全素材に `url` あり | URL を補完、不可なら除外 |
| 6 | **重複** | 同一ニュースの重複なし（要約統合可） | 統合 |
| 7 | **索引完全性** | `00-manifest.md` の行数 ＝ `collection/` 内の素材ファイル数 | 整合 |
| 8 | **DB 定期データの鮮度** | 当日参照する Tier B（財務／マクロ／カレンダー／目標株価）が DB 上で FRESH（`now < effective_until`）。STALE/欠損は能動更新で解消（3.9.3〜3.9.4） | 該当データを能動更新 |

> 「宁可多取」原則により、**量の超過は不合格理由にならない**。不合格は「漏れ」または「形式不備」のみ。ただし Tier B データは「毎日再取得」ではなく DB キャッシュで供給する（3.9）ため、検査8 は「当日分として fresh か」のみを問う。

### 3.9 ローカルデータベース層（定期更新データの最適化）

#### 3.9.1 課題と設計意図

現状の収集は**毎日すべての情報源を起点に最新情報を取得**するが、データの性質によっては非効率であり、かえって精度を落とす：

- **決算財務データ**: 直近の決算発表後、次の決算までは**数値が変化しない**。毎日再取得するのは無駄であり、一時的なソース揺らぎで確定値が汚染されるリスクすらある。
- **マクロ経済指標**: CPI・雇用統計・GDP 等は**発表サイクルが固定**（月次・四半期）。発表日前後以外は値が不変。
- **アナリスト目標株価／レーティング**: 日々変動するが、コンセンサス水準は準静的。
- **経済カレンダー**: FOMC・指標発表日は**事前に既知**。

これら「定期更新データ」をローカル DB にキャッシュし、**変化がない限り再取得せず、変化があった瞬間だけ更新**する層を設ける。狙いは3点：

1. **取得の効率化** — 変わらないデータの再クロールを排除。
2. **確定値の保護** — 一度確定した財務/マクロ数値を不変として保持し、精度を担保。
3. **大モデルによる検索の容易化** — 構造化表として保持し、SQL で自在に検索。

> 本層は Phase 0（collector）が主に読み書きするが、Phase 2（scriptwriter）がバリュエーション履歴を引くなど**日をまたぐ共有資産**でもある。したがって日次ワークスペース（`daily-output/YYYY-MM-DD/`）の外、プロジェクト直下 `db/` に置く。

#### 3.9.2 データの鮮度モデル（3階層）

収集対象を鮮度で3階層に分類し、階層ごとに保存先と更新戦略を変える。収集エージェントは各データがどの階層かを判定し、Tier B は必ず DB を経由する。

| 階層 | 例 | 鮮度 | 保存先 | 更新戦略 |
|------|----|------|--------|----------|
| **Tier A 変動** | 株価・為替・騰落率・ニュース速報 | 秒〜日次 | 当日 `collection/`（既存） | 毎日新規収集 |
| **Tier B 定期** | 決算財務・マクロ指標・アナリスト合意・経済カレンダー | 四半期／月次／イベント | **DB（本節）** | 定期＋オンデマンド |
| **Tier C 参照** | セクター分類・バリュエーション手法 | ほぼ不変 | `data-sources/`（既存 markdown） | 手動更新 |

#### 3.9.3 フレッシュネス判定（核心ロジック）

Tier B の各レコードは以下のメタを持ち、**時間ベースの推測なしに**新鮮／陳腐化を判定する。

| 列 | 意味 | 例 |
|----|------|----|
| `period` / `as_of` | そのデータが記述する期間 | 2026 Q2 / 2026-06 |
| `effective_until` | **このデータが有効な期限（＝次回更新予定日）** | 次回決算日 / 次回 CPI 発表日 |
| `fetched_at` | 最終取得日時 | 2026-07-14T06:30 |
| `source` | 取得元 | SEC EDGAR / FRED |

**判定規約:**

- `now < effective_until` → **FRESH**（キャッシュ命中。再取得しない）
- `now >= effective_until` → **STALE**（更新対象）

> これが「決算発表後は変わらない」を構造で表現する。財務の `effective_until` に**次回決算日**を入れておけば、システムは次の決算まで再取得しないことを自動的に知る。マクロ指標の `effective_until` に**次回発表日**を入れておけば同様。これが本最適化の核心（財務・マクロの無駄な再取得排除）である。
>
> 各データセットの周期・情報源・`effective_until` の算出方法・次回予定日は管理表 `data_catalog` に一元管理する。

#### 3.9.4 二つの更新機構（定期更新＋能動更新）

両機構は同じ DB に書き込むため、常に「1回書けば何度でも読める」状態になる。

**① 定期更新（スケジュール駆動）** — 効率的な主経路

- Phase 0 開始前に `db/refresh.py` を実行（cron でも手動でも可）。
- `data_catalog` を走査し、`effective_until <= now`（または先読み窓内）のデータセットを**一括**更新。
- 一度更新すれば全日で再利用できる。これを毎朝 Phase 0 の前に回すのが基本運用。

**② 能動更新（オンデマンド）** — フォールバック

- 後段エージェントが `db/db_access.py` の取得関数を呼ぶ。
- 関数内部で鮮度を判定し、FRESH なら DB から即返却、STALE／未登録なら**その場で取得して保存してから返却**する。
- 定期バッチが取りこぼしたデータを必要になった瞬間に補う。

#### 3.9.5 DB エンジン選定: SQLite

| 要件（ユーザー指定） | SQLite の適合 |
|------|---------------|
| ファイル型・システムを複雑にしない | 1ファイル・サーバ不要・設定ゼロ |
| リレーショナル／オブジェクト | リレーショナル＋SQL（大モデルは SQL 生成に極めて習熟） |
| 大モデルによる検索容易性 | 標準 SQL で自在検索。ビュー→JSON／Markdown エクスポートも容易 |
| 既存環境との統合 | Python 標準 `sqlite3`・追加依存ゼロ（`analyze_benchmark.py` と同環境） |

> DuckDB（分析特化）や純 JSON も候補だが、「複雑排除＋検索容易」の要件には SQLite が最適。将来の分析負荷が増大した場合は、read-only で DuckDB から同一ファイルを参照可能（移行が容易）なので、まず SQLite で始める。

#### 3.9.6 スキーマ（表構成）

DB ファイル: `us-stock-daily/db/market-data.sqlite3`（プロジェクト直下・日次ワークスペース外）

**データ表:**

| 表 | 主キー | 内容 | 鮮度階層 |
|----|--------|------|----------|
| `tickers` | ticker | 追跡銘柄マスター・セクター分類・`next_earnings_date` | Tier B（準静的） |
| `company_financials` | (ticker, fiscal_period) | 四半期財務（売上・EPS・マージン・FCF・BS項目） | Tier B（四半期・決算駆動） |
| `macro_indicators` | (series_id, period) | マクロ時系列（CPI／PPI／NFP／GDP／FedFunds …） | Tier B（月次／四半期・発表駆動） |
| `economic_calendar` | event_id | 経済イベント（指標名・時刻・予想・前回・実績） | Tier B（イベント駆動） |
| `analyst_consensus` | (ticker, fetched_at) | コンセンサス目標株価・レーティング分布・EPS 予想 | Tier B（日次スナップ・小容量） |

**管理表:**

| 表 | 内容 |
|----|------|
| `data_catalog` | データセットごとの更新ポリシー（周期・情報源・`effective_until` 算出法・次回予定日・`last_fetched`・スキーマバージョン） |
| `fetch_log` | 取得監査ログ（何をいつ取得したか・ソース負荷管理・デバッグ用） |

**LLM 向けビュー（事前定義）— 大モデルが JOIN なしで検索できる入口:**

| ビュー | 用途 |
|--------|------|
| `v_latest_financials` | 銘柄ごとの最新財務1行 |
| `v_macro_latest` | マクロ系列ごとの最新値 |
| `v_upcoming_events` | 直近の経済カレンダー（前方） |
| `v_stale_datasets` | 更新が必要なデータセット一覧（定期バッチが読む） |

#### 3.9.7 大モデル検索インターフェース

「大モデルが検索しやすい」を具体化する2経路を用意する。

**経路A — Python 関数（推奨）:** `db/db_access.py` が鮮度を隠蔽した薄い API を提供。エージェントは「鮮度」を意識せずデータを取得できる。

```python
get_fundamentals(ticker, as_of=None)   # 財務（鮮度自動判定・STALE なら能動更新して返す）
get_macro(series_id, as_of=None)       # マクロ指標
get_calendar(date_from, date_to)       # 経済カレンダー
get_consensus(ticker)                  # アナリスト合意・目標株価
```

**経路B — 直接 SQL:** エージェントがビューに対し SQL を発行。`db/QUERY_GUIDE.md` に「よくある質問 → SQL」のチートシートを用意する（例: 「NVDA の最新四半期財務」→ `SELECT * FROM v_latest_financials WHERE ticker='NVDA'`）。

> Phase 0／2 のエージェントはいずれかの経路で DB を読む。取得結果は必要に応じて当日素材（markdown）にも転記し、鉄則二（大手目標株価の明示）の原料とする。

#### 3.9.8 データの住み分け（何を DB に、何を当日素材に）

| データ | 保存先 | 理由 |
|--------|--------|------|
| 株価・為替スナップ | 当日 `collection/`（MKT） | 日次変動（Tier A） |
| 四半期決算財務 | **DB** `company_financials` | 発表後不変（Tier B） |
| マクロ指標（CPI 等） | **DB** `macro_indicators` | 発表サイクル固定（Tier B） |
| 経済カレンダー | **DB** `economic_calendar` | スケジュール既知（Tier B） |
| アナリスト目標株価／レーティング | **DB** `analyst_consensus` | 準静的（Tier B） |
| ニュース速報 | 当日 `collection/`（NWS） | 一時的（Tier A） |
| リサーチ本文・解説 | 当日 `collection/`（RES／STK） | ナラティブ・非構造（Tier A） |

```
├── schema.sql              # スキーマ定義（コミット対象・再現性の源泉）
```

- `data_catalog` にスキーマバージョンを持ち、簡単なマイグレーションで運用する。

#### 3.9.10 Phase 0 との統合（収集サブワークフローへの組み込み）

本層は 3.6 の収集サブワークフローに「DB ヘルスチェック」ステップを追加して統合する（3.6 のステップ 0.5 を参照）。collector は以下のように振る舞う：

- **マクロ／決算／経済カレンダー／目標株価** → まず DB を参照。FRESH なら再取得せず、当日素材の `key_data` に DB 値を転記。STALE なら能動更新。
- **当日発表のマクロ実績値**（CPI 実績など） → 発表後に DB を更新**し**、当日素材（MAC）にも記録。
- **株価スナップ・ニュース・リサーチ本文** → 引き続き毎日新規収集（Tier A）。

> Gate #0（3.7）の網羅性検査は「DB 上の定期データが当日分として fresh であること」を含める（検査項目8 を追加）。

### 3.10 ブランドロゴ資産キャッシュ（assets/brands）

#### 3.10.1 課題と原則

毎日の番組で**同じ企業ロゴ・メディアロゴ**（Bloomberg, WSJ, Goldman Sachs, NVDA …）を何度も検索・ダウンロードするのは無駄である。ロゴはブランド刷新時以外は**ほぼ不変**（3.9.2 の Tier C 参照に相当）。したがって 3.9 の定期データ層と同じ「**取得1回・キャッシュ再利用**」原則を適用するが、鮮度期限は持たず**ファイルの存在だけで判定**する（バイナリを DB に抱えず、ファイル＋マニフェストで管理）。

> **核心フロー**: ロゴが必要 → `assets/brands/` を確認 → **あれば再利用（再取得しない）／なければ検索DL → 保存 → 次回からキャッシュ命中**。

#### 3.10.2 ディレクトリ構成（プロジェクト直下・全日共有）

```
us-stock-daily/assets/brands/        # 日次ワークスペースの外・全エピソードで共有
├── companies/                        # 企業ロゴ（ticker 別）
│   ├── nvda.png
│   ├── aapl.png
│   └── ...
├── media/                            # メディア・情報源ロゴ（出所表示用）
│   ├── bloomberg.png
│   ├── wsj.png
│   ├── goldman-sachs.png
│   └── ...
└── manifest.md                       # キャッシュ一覧＋取得元URL＋ライセンス/使用条件
```

> **`assets/` の2系統に注意**: 本ディレクトリ `assets/brands/` は**プロジェクト直下の共有キャッシュ**（ロゴ等の不変資産）。各日の `daily-output/YYYY-MM-DD/assets/` は**その回限定**のスクリーンショット／チャート（Phase 3 が都度取得）。混同しないこと。

#### 3.10.3 命名規約

- ファイル名 = 正規化スラッグ（小文字・ハイフン区切り）。企業は ticker 小文字（`nvda.png`）、メディアはケバムケース（`goldman-sachs.png`）。
- 形式は **背景透過 PNG／SVG** を優先（番組のカラーコード背景に重ねるため）。同名で PNG と SVG が両方ある場合は PNG を標準とし SVG を併存可。

#### 3.10.4 取得フロー（Phase 3 asset-fetcher が実装）

```
ロゴが必要になった時:
1. assets/brands/{companies,media}/<slug>.png の存在確認
   - あり → そのまま使用（再取得しない）★ キャッシュ命中
   - なし → 手順2へ
2. 検索・ダウンロード（優先順: 公式IR／プレスキット／ブランドアセットページ → Wikipedia → ロゴ検索）
3. 所定パスへ保存 → manifest.md に1行追記（slug / 種別 / 取得元URL / 取得日 / 使用条件）
4. 保存したファイルを使用
```

#### 3.10.5 マニフェスト（manifest.md）

キャッシュ一覧と出所の透明性を保つ。Gate 検査・ライセンス確認・「どこから取ったか」追跡の原料。**保存時の1行追記を必須**とする（追記なきキャッシュ追加は禁止）。

```markdown
# ブランドアセットキャッシュ一覧
| slug | 種別 | 取得元URL | 取得日 | 形式 | 備考（ライセンス／使用条件） |
|------|------|-----------|--------|------|------|
| nvda | company | https://nvidianews.nvidia.com/... | 2026-07-14 | PNG | IRページ、ブランドガイドライン準拠 |
| bloomberg | media | https://bloomberg.com/... | 2026-07-14 | PNG | 出所表示用、改変禁止 |
```

#### 3.10.6 既存設計との統合

- **3.2 遅延取得戦略**: 「企業ロゴ」は Phase 3 で取得するが、取得先は都度 Web ではなく **`assets/brands/` キャッシュを優先**（キャッシュミス時のみ検索DL）。
- **Phase 3 asset-fetcher（第四章）**: 入力判定に「brands キャッシュ参照」ステップを追加。チャート／スクリーンショット（回限定・Tier A）は引き続き各日 `assets/` へ。
- **6.6 視覚表現規範**: 出所表示・企業ロゴ表示の素材は `assets/brands/` から取得する旨を明記。
- **バージョン管理**: 不変資産かつ再現性が重要なので基本コミット対象。容量が大きくなった場合は Git LFS を検討。

#### 3.10.7 3.9 DB 層との対比（同じ原則・異なる実装）

| | 3.9 定期データ DB | 3.10 ブランドロゴキャッシュ |
|--|------------------|-----------------------------|
| 対象 | 財務・マクロ・目標株価（構造化数値） | 企業・メディアロゴ（画像バイナリ） |
| 鮮度 | Tier B（定期更新・`effective_until` で管理） | Tier C（ほぼ不変・存在ベースで判定） |
| 実装 | SQLite + 鮫度API | ファイル + manifest.md |
| 更新 | 定期バッチ＋能動更新 | キャッシュミス時のみ取得 |
| 共通点 | **プロジェクト直下・全日共有・取得1回で再利用** | 同左 |

## 四、Phase 1〜5：制作・検証フェーズ（後日補完）

> 各 Phase の詳細要件は後日追加する。下記は骨子のみ。仕様確定時、対応する `templates/phaseN-spec.md` へ切り出す予定。

### Phase 1：テーマ選定・構成（triage-agent）

Phase 1 は「収集した素材群から当日の話題を **抽出・評価・順位付け** し、コーナー割当を決める」フェーズ。ここが番組の質を決める最大の分岐点。collector の「宁可多取」で集めた素材から、本質的な少数（3-5 話題）を絞り込む。

- **入力**: `collection/`（Phase 0 の全素材）＋ `00-manifest.md` ＋ DB の定期データ（3.9）
- **出力**: `production/outline.md`
  - 選定された **3-5 話題**（A の核心予告の原料。各1文の問い形式で記述）
  - 各話題の主内容コーナー（B/C/D/E）への割当と優先度（A/B/C）
  - サスペンスフック（各話題を問いで表現）
  - **直近イベント予告の要否判定**（直近3営業日に重要イベントがあるか。DB `economic_calendar` 参照）

#### 選題原則（話題の評価軸）

候補話題を以下の原則で評価し、順位付けして上位 3-5 を選ぶ。原則は **影響力・需要・供給・実行性** の4群。**原則 e（情報非対称価値）は番組の存在意値そのもの** — 視聴者が自分で Finviz を開けば分かる「流水帳」を番組で繰り返しても価値はゼロであり、专业化・クロスマーケット連関・歴史類推こそがエッジである。

**① 影響力 — 市場の意味を捉えるか**
- a. **前日メインロジックの深層**: 前営業日の主な取引ロジックとその深層原因を説明できるか（市場が「なぜ」動いたか）。
- b. **将来への重大影響**: 後市に重大な影響を与えうる特定イベント・トレンド・心理の変化を含むか（方向性を変えうる素材）。

**② 需要 — 観客が知りたいか**
- c. **散户の関心度**: 個人投資家が最も関心を持つ／不安を感じるテーマか。
- d. **時事性・鮮度**: 今日新しい情報か（古い話題の単なる延長は、転換点にある時以外は劣後）。

**③ 供給 — 番組の独自価値（最重要）**
- e. **情報非対称価値**: 散户が自力では取得／理解困難な内容か。**指数の羅列など視聴者が自力で得られる「流水帳」は原則除外**。
- f. **深掘り素材の品質**: 背後に高品質・高価値な深掘り記事／機関リサーチがあるか。
- g. **独立性・反直観**: 市場コンセンサスに対し独自／対立的視点を提供できるか（認知のズレを修正する価値）。

**④ 実行性 — 番組理念との整合**
- h. **可操作性（鉄則二接続）**: 具体的アクション指針（目標株価・買い・積み増し・損切り水準・ポジション）に落とせるか。
- i. **教学価値**: 再利用可能な投資の枠組み／方法論を教えられるか（長期投資教育の理念）。
- j. **防守視点**: 隠れたリスク・過密トレード・バリュエーションの行き過ぎを表面化できるか（散户を守る）。

#### 順位付けモデル

各候補話題を主要軸（例: 影響力 a/b × 需要 c × 供給 e/f × 実行性 h）で **0-3 点** で採点し、重み付き合計で順位付けする。上位 3-5 を A の核心予告に、さらにその上位を主内容コーナー（**D を核心**、必要に応じ B/C/E）に割り当てる。採点根拠は `outline.md` に残し、Gate #1 で検査する。

> **選題の目安**: 1話題あたり主内容 5-15分。30-40分番組では主内容ブロックは **2〜4本** が現実的。D（核心・10-15分）を毎日据え、残り枠を B/C/E から当日の評価順に埋める。

- **Gate #1**: 選題原則による採点が記録されている / 核心予告 3-5 話題が確定 / D（核心）に話題が割り当て済み / 各話題にサスペンスフック付与済み / 直近イベント予告の要否が判定済み。

## 五、二つの鉄律（全 Phase 共通の制作不変原則）

### 鉄則一：オープニングの核心予告＋サスペンス作り

30-40分の長尺番組では、冒頭は**指数の羅列（流水帳）で終わらせない**。視聴者が自力で得られる情報（各指数の騰落率など）は省き、**自然言語で前日市況の意味を総括し、本日掘り下げる3-5話題を各1文で予告**してサスペンスを作る（美投君スタイル）：

1. **前日市況の総括** (30秒-1分): 自然言語で「市場の主な動きとその理由」を1-2文で。**指数の羅列はしない**（視聴者が自力で取得可能＝番組の価値ではない）。
2. **核心予告** (1-2分): Phase 1 が選定した 3-5 話題を、それぞれ核心となる問いを **1文** で要約。「本日はこの N 個のポイントを深掘りします」と視聴者に路線図を示す。
3. **表現形式は内容に従属**: 内容が俳句で凝縮できる時は **俳句形式**（ブランド要素・5-7-5音）、情報量が多く短い句にまとまらない時は **通常の口語**。俳句は独立コーナーではなく A の表現形式の一つ。

> 話題の選定基準は **Phase 1 の選題原則（第四章）** による。核心予告で予告した話題は、そのまま主内容ブロック（B/C/D/E）で深掘りされる ― 予告と本編が1本の線で繋がる。

### 鉄則二：個別株／セクター分析には大手目標株価＋具体的アクション価格を必ず示す

個別株・セクター指数の分析には**必ず**含める：
1. **大手目標株価**: 少なくとも1社の著名投資銀行の目標株価とレーティング（Phase 0 の `RES-`/`STK-` 素材が原料）
2. **具体的アクション指針**: 明確な買い建て／積み増し／縮小／損切りの価格水準
3. **ポジション目安**: ポジション比率または分割買い戦略

> 鉄則二の原料は Phase 0 で「宁可多取」で集めたレーティング・目標株価素材。収集時点で `key_data` に目標株価・レーティングを入れておくこと（Gate #0 の網羅性検査の対象）。

> 以降は制作フェーズ（Phase 1〜5）が参照する共通仕様。各 Phase を詳細化する際、対応仕様書へ分割予定。

### 6.1 コーナー構成と時間配分 (30-40分)

番組は **固定フレーム（枠）** と **主内容ブロック（B/C/D/E から選択）** の2層で構成する。固定枠が番組の骨格（毎日同じ位置・同じ役割）、主内容ブロックが当日の話題に応じて選択される肉付け。

#### 【固定フレーム（枠）】— 番組の開始と終了を担う。毎日同じ位置。

| 放送順 | コーナー | 時間 | 核心定位 |
|--------|----------|------|----------|
| 1 | **A. オープニング**（旧 OP＋A 統合） | 2-3分 | 前日市況を**自然言語**で総括 → **3-5話題を各1文**で予告 → サスペンス。**俳句は内容が合致する時の表現形式の一つ（任意）** |
| — | *（この間に主内容ブロックを挿入）* | — | — |
| 2 | **F. ニュース速報レビュー** | 2-3分 | 8本の精選ニュース、各30字以内、重要度順（最重要を最後に） |
| 3 | **直近イベント予告**【新設・非固定】 | 0-2分 | 直近 **3営業日** の重要イベント（マクロデータ発表・主要銘柄決算等）の日付を羅列。**該当なければスキップ**（DB `economic_calendar` 参照） |
| 4 | **G. エンディング** | 1分 | まとめ＋免責＋次回予告 |

#### 【主内容ブロック】— 以下 B/C/D/E から当日の話題に応じて **2〜4本を選択** し、A と F の間に配置。

| コーナー | 時間 | 頻度 | 核心定位 |
|----------|------|------|----------|
| **B. マクロ深層分析** | 5-8分 | 選択 | 当日最重要マクロテーマを掘り下げ |
| **C. 大手リサーチ精選** | 5-8分 | 選択 | 影響力ある機関見解を解説 |
| **D. 個別株／セクター深層分析** | 10-15分 | 選択（**核心・毎日採用推奨**） | 業界縦深＋バリュエーション＋**アクション指針** |
| **E. 投資戦略とリスク管理** | 3-5分 | 選択 | ポジション管理、心理、リスク警告 |

> 話題の選定とコーナー割当は **Phase 1（triage-agent）** が **第四章の選題原則** に従い決定する。A で予告した話題が主内容ブロックの各コーナーに割り当たる。

#### 構成変更の要点（v4.3）

- **OP は A に統合**: 俳句は独立コーナーではなく **A の表現形式の一つ**。当日の内容が俳句で凝縮できる時は俳句、情報量が多く短い句にまとまらない時は口語で前日市況を総括。俳句を採用する場合の「全コーナー完成後に制作」タイミングは維持。
- **流水帳の禁止**: A で各市場の指数を羅列しない（「SPX +x%、NDX …、DXY …」のようなスキャン）。それらは視聴者が自力で取得可能であり番組の価値ではない。A は自然言語で「市場の主な動きの理由と、本日掘り下げる3-5話題」に絞る。個別の数値データは主内容ブロック（B/D 等）で文脈付きで扱う。
- **E の位置づけ変更**: E は「毎日固定」から「主内容ブロックの選択肢」へ。ただし基本となるリスク警告・免責要素は固定フレーム（G 等）に常に含まれるため、E を省いても守備のコンプライアンスは担保される。
- **動的調整**: D は核心なので毎日採用を推奨。決算シーズンは D 拡大＋C 起動。FOMC 週は B 拡大。ブラックスワン時は B/E を厚く。主内容が薄い日は B/C/E を減らして D を深掘りし時間を確保する。

### 6.2 各コーナー制作方法論（解説フレームワーク）

- **A. オープニング**: 前日市況を自然言語で総括（**指数羅列しない**） → Phase 1 選定の **3-5話題を各1文で予告**（問い形式でフック） → サスペンス。俳句形式は内容が合致する時のみ（全コーナー完成後に制作）。
- **B. マクロ深層**: 背景 → 前回/予想/実績 → 市場反応 → 深層解読 → 歴史比較 → 結論
- **C. 大手リサーチ**: アナリスト背景 → 核心見解 → 論拠 → 目標株価 → 当番組の判断 → アクション指針
- **D. 個別株/セクター**: 概要 → 業界位置付け → 核心データ → 競争環境 → バリュエーション → 大手目標株価集計 → **アクション指針** → リスク → まとめ
- **E. 戦略/リスク**: 心理温度計 → リスク警告 → ポジション目安 → 古典的知恵
- **F. ニュース速報**: 8本、各30字以内、重要度順（最重要を最後に）
- **直近イベント予告**: DB `economic_calendar` から直近3営業日の重要マクロ発表・主要銘柄決算を抽出し、日付＋件名を簡潔に羅列。該当なければコーナー自体をスキップ。

### 6.3 バリュエーション方法論（業界別 — Dコーナー核心）

業界が違えば測る物差しも違う（詳細は `data-sources/sector-valuation-guide.md` 参照）：

- **タイプ1 高成長期** (AIインフラ・先端半導体・量子等): PSR, P/FCF, EV/Revenue, TAM浸透率, ユニットエコノミクス, 遠期利益割引。売上成長・TAM拡大・技術モートに焦点。
- **タイプ2 成熟成長期** (大型テック・SaaSリーダー等): 予想PE, PEG, DCF, EV/EBITDA, ユーザー/加入者価値。
- **タイプ3 シクロ** (エネルギー・素材・工業・海運等): 標準化PE, PBR, サイクル位置指標, 配当利回り。ピーク時の低PEは売りシグナルに注意。
- **タイプ4 ディフェンシブ/インカム** (公益・必需品・ヘルスケア・REIT): DDM, P/FFO, 利回り格差分析。

### 6.4 アクション指針出力規範（鉄則二の具体形）

```
「[銘柄] の私のアクションプランは：
- [大手] の目標株価 [XX] ドルを中期の方向性として参考にします
- 現在 [XX]。[大手] の最低指導価 [XX] ドル付近で [X%] の初期ポジションを構築します
- [X%] 押し戻されて [XX] 付近なら、[X%] まで積み増します
- 損切り: [XX]（[X%] 移動平均／主要サポートを下抜け）
- 第1目標値 [XX]（+XX%）、到達で半分利確。最終目標値 [XX]（コンセンサスと一致）」
```

買い／縮小／様子見の各シナリオを用意。コンプライアンス（第八章）に従い「私ならこう動きます」形式。

### 6.5 スクリプトテンプレート
