## 三、「微软AI营收依赖OpenAI」漏收的机制性复盘

这篇华尔街见闻文章是最佳案例，漏收是三层原因叠加的必然结果:

1. **信源没有被访问**: 该文章发布在 wallstreetcn.com/news/us-stock —— account-checklist.md
   中明确登记「カバー: 米国株、半導体、AI、マクロ、企業深層分析」「Dセクター深層分析素材に適する」。
   但执行从未访问该信源。**信源驱动收集不存在，漏收是时间问题。**
2. **查询驱动的天然盲区**: 查询式搜索只能找到「我想到要问的东西」。我没有查询
   「微软 OpenAI 营收依赖」，因为我不知道有这篇文章。这正是信源驱动收集要解决的
   「未知の未知」问题——靠想题目永远想不全。
3. **查询集偏向事件面**: 今天的12个查询全部围绕「市场事件」（霍尔木兹/ISM/联储/AMD/日元），
   没有任何一个查询覆盖「科技商业模式/产业链深度」维度。即便只做查询，维度设计也不完整。

**结论**: 这不是偶发遗漏，是收集架构缺失的必然产物。今天漏的是这篇，明天会漏下一篇。

## 四、根因分层

### 1. 执行层缺失（最直接）: 没有 collector 实现
Phase 0 是纯文字规范，**没有任何脚本/工具去迭代信源清单**。人工执行时只能依赖手头工具
（查询式搜索），收集范围被工具的形态限死。「宁可多取」原则没有任何执行载体。

### 2. 规范层断裂: 信源清单与收集流程脱节
- account-checklist.md 有详细登记（URL、访问方法、内容过滤基准、适用板块），
  但 phase0-collection.md 的收集子工作流**完全没有引用它**——Phase 0 引用的是
  info-sources.md（只有信源名称，没有访问方法）。两份文档之间没有可执行的桥。
- 「固定放送资产」检查只覆盖了宏观/行情维度，没有「必须信源逐个过」的检查项。
- 正文全文要求（「本文テキスト＋URLを保存」）没有任何 Gate 检查项去强制，
  所以我存了索引也能过 Gate #0。

### 3. 判断层错误（我的责任）
- 8/4 试跑被批评的是「分析深度」，我修复了 Phase 1.5/Phase 2 的深度与标注，
  但**默认收集环节「工具链通了就行」**——这个假设是错的，收集广度从未被修复。
- Gate #0 数量不达标时，规范写明处置是「追加收集」，我却以「通道受限」为由放行。
  这是用客观限制合理化执行缩水。正确做法是: 不合格→继续收集→直到达标或明确记录
  无法达标的边界。
- 「跑完全流程」被置于「收集充分」之上，优先级排错了。用户的铁则写得很清楚。

### 4. 工具层约束（真实但次要）
- SearXNG 故障＋gcloud 过期使查询通道降级（用户在另一会话部署本地 SearXNG 解决中）。
- 但即使 SearXNG 正常，**查询式搜索也只是补充手段**，替代不了信源驱动的全量收集。
- longbridge 覆盖行情/财报/评级类结构化数据（今天已用好），不覆盖文章。
- 晨报邮件（Bloomberg/WSJ/Yahoo/Reuters/SemiAnalysis）在用户邮箱里，
  目前**没有任何机制把邮件内容送进流水线**——这是一个独立的缺口（见修正方案5）。

## 五、修正方案（待确认后实施）

### 1. 机器可读的信源登记簿 `data-sources/source-registry.json`
每个信源一条记录: id / 名称 / URL或入口 / 类型（homepage-crawl / rss / api / email / browser）/
语言 / 访问方法（direct HTTP / agent-browser / 用户导出）/ 内容过滤基准（照抄 account-checklist）/
类目映射 / 优先级（must-crawl 必须遍历 / nice-to-have）。
从 account-checklist.md 已验证的信源开始录入（华尔街见闻、36氪、GS/MS/JPM/BlackRock、
Reuters/CNBC RSS 等）。

### 2. 收集器 `tools/collect.ps1`（或 Python）
遍历登记簿 → 按各信源的访问方法抓取最新条目 → 每条一个素材文件（标题/URL/**全文**/来源/时间）
→ 自动生成 manifest 骨架。信源驱动为主，查询式搜索为事件补充。
（华尔街见闻/36氪为 JS 渲染站，优先找其 API/RSS 端点，不行则用 agent-browser 技能。）

### 3. 正文全文强制要求
素材格式中「## 原文抜粋」升级为「## 全文（または実質的な全文抜粋）」；
Gate #0 新增检查项: 素材正文长度下限（如 ≥500字）＋正文非空率 100%。

### 4. Gate #0 硬化
- 数量基准不可用「通道受限」豁免: 不达标 → 追加收集轮次 → 仍不达标则逐条记录
  「已尝试的信源与失败原因」，而不是笼统的「条件PASS」。
- 新增「必须信源覆盖」检查: must-crawl 信源逐个确认「有收获」或「今日无更新」，缺一即不合格。

### 5. 晨报邮件的输入机制（需要用户决策）
Bloomberg Five Things / WSJ Markets A.M. / Yahoo Morning Brief / Reuters Morning Wire /
SemiAnalysis 都在用户邮箱。可选方案:
- a) 用户每日手动转发/导出到约定目录（最简单可靠）
- b) agent-browser 技能登录网页邮箱抓取（自动化但需要会话维护）
- c) 邮件→文件的自动同步工具（如用户环境有 IMAP 条件）

### 6. SearXNG 定位
本地 SearXNG（用户部署中）恢复后作为**查询补充通道**（事件追踪、交叉验证、补漏），
信源驱动收集仍是主干。两者不冲突。

## 六、验收标准（修正后的 Phase 0 应该是什么样）

以「微软AI营收依赖OpenAI」这类文章为测试用例: 修正后的收集流程应当在**没有任何人
预先想到这个选题**的情况下，通过遍历华尔街见闻当日文章列表把它收进来，带全文、带URL、
带来源，等待 Phase 1 评分筛选。能做到这一点，才说明「宁可多取」真正落地了。
